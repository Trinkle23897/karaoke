# 视频链接 → 卡拉 OK 成品

本地异步 API，复用当前 F + Anvuew 三轨分离、音频歌词对齐和金色字幕流程。

各计算阶段按代码、配置、模型与输入指纹复用检查点；运行版本以 `/health` 的 `pipeline_version` 和任务记录为准。普通播放保存底轨（背景音乐＋伴唱）与主唱两轨，严格音频验收可另外输出独立三轨。音质与逐字起音的评测方法见[验收标准](ACCEPTANCE.md)和[自动质量检查](docs/automatic-quality.md)。

## 启动

在仓库根目录运行：

```sh
.venv/bin/python -m pip install -r karaoke/requirements-api.txt
.venv/bin/python -m karaoke.api
```

默认监听 `127.0.0.1:8746`。网页点歌台：<http://127.0.0.1:8746/>。交互文档：<http://127.0.0.1:8746/docs>。
API 的依赖文件只安装服务依赖。新检出请按[安装说明](../SETUP.md)准备模型、音频环境和 FFmpeg；模型权重和歌曲数据不在仓库中。

## 网页与共享歌单

网页使用 `GET /v1/room/events` 的 SSE 长连接，不轮询。初次连接和漏过更新时收到 `room` 完整快照；连续更新收到 `room_patch`。同一次状态变化共用一次快照读取和 JSON 编码。

完整快照带 `stream`（服务实例标识）和 `sequence`（推送序号，区别于命令的 `revision`）。补丁带同一 `stream`、`base`、`sequence`、`changes` 和 `collections`：`changes` 替换顶层字段；`entries`、`history`、`library` 按 ID 提供 `upsert`、`remove`，顺序变化时另给完整 ID `order`。包含重复 ID 的旧列表直接整体替换。客户端只有持有同一流的 `base` 才应用补丁，否则重连取完整快照。`server_time` 和本连接的 `playback_entry` 随每帧发送，不放进共享缓存。慢连接只保留一次更新通知，不累积补丁队列。每份共享快照的待唱列表和曲库复用同一批任务记录，目录信息只读取一次。

曲库按索引读取排队／运行任务、已完成／可恢复媒体及所有待唱项，并补齐这些来源的最新记录；任务总数超过 1,000 条也保留旧成品。没有成品媒体且已移出待唱的历史失败不参与快照，任务记录和检查点仍保留，供查询及再次点歌时复用。

断线重连采用有随机抖动的指数退避（起始 0.5–1 秒，上限 15–30 秒）；45 秒未收到数据或心跳也进入退避。收到有效状态或心跳后重置退避。下面的 `GET /v1/jobs/{id}` 仍供脚本按需查询。

处理中的房间条目和曲库歌曲通过 `preparation_started_at` 提供本次开始时间（ISO 8601），其他状态为 `null`。前端结合快照的 `server_time` 校正时钟并显示累计用时，不额外轮询；重试使用新一次处理的开始时间。

房间条目的 `lyrics_unavailable` 表示成品没有可显示字幕；`lyrics_need_review` 表示歌词或对齐尚待复核，两者不能混为同一个提示。

| 接口 | 用途 |
|---|---|
| `GET /v1/library` | 按来源列出当前任务及已准备／待恢复歌曲，实际文件完整时才标记为已准备 |
| `GET /v1/room` | 待唱 `entries`、倒序演唱记录 `history`、准备状态和兼容旧客户端的播放字段 |
| `POST /v1/room/entries` | 传入 `{ "url": "..." }` 点新歌，或 `{ "job_id": "..." }` 复用已准备歌曲 |
| `POST /v1/room/commands` | 网页共享操作：`finish`、`remove`、`reorder`、`retry`、`reprepare`；另保留旧客户端播放命令 |
| `GET /v1/room/events` | 推送 `room` 完整快照、`room_patch` 增量更新；空闲时发送 `ping` |
| `GET /v1/storage` | 缓存使用量、上限、受保护与可回收容量、准备空间是否足够 |
| `POST /v1/storage` | `{ "limit_gib": 10 }` 修改并持久化上限；`null` 取消应用配额，仍保护实际磁盘余量，返回新的房间快照 |

兼容旧客户端的 `pause`、`seek`、`next`、`ready` 必须带 `entry_id`，防止旧播放器事件影响新歌曲。`reorder` 传入完整的 `order` ID 数组，可带 `revision` 拒绝过期操作；调序不改变设备正在播放的歌。`mix` 接受 `instrumental`（纯伴奏）、`karaoke`（伴奏＋伴唱）、`original`（三轨一起播放）。

网页不使用服务端的 `current_id`、`playing`、`position`、`started_at`、`mix`、`levels`、`pitch_semitones` 控制播放。这些旧 API 字段仅为兼容保留；网页的播放命令、媒体就绪握手和缓冲处理全部在设备本地进行。播放状态经 localStorage 在同一浏览器标签页间共享，只有取得发声权的标签页播放；搜索与页面导航状态保存在各标签页的 sessionStorage。刷新后仍受浏览器声音授权限制，不跟随其他设备起播。

跳过仍在准备的歌只改变本机选曲，原条目留在待唱。已准备的歌切到下一首或唱完时发送 `finish`；明确点击「移除」发送 `remove`。两种命令都绑定 `entry_id`，浏览器保存原命令直到服务端确认，刷新后也可重试。同一条目只移除一次。实际起播时间 `playback_started_at` 以 Unix 秒计；尚未开唱时传 `null`，不新增已唱记录。

`GET /v1/room/events?job_id=…` 在 SSE 存续期间保护本机当前歌曲的缓存，并在快照的 `playback_entry` 中推送该任务的最新元数据；即使该歌曲不再位于共享待唱列表，也保持可播放。关闭连接释放保护，连接和状态推送不刷新 LRU 访问时间。

`history` 与房间一起持久化并通过 SSE 推送，最新唱过的排在前面。每次演唱保存独立的条目 ID、任务 ID、来源 URL、歌名、歌手、语言、时长、封面和 Unix 秒时间 `played_at` / `finished_at`。开始播放后切歌、结束或移除当前歌曲才归档；加载、开场倒计时或准备中直接跳过不归档。`select` 会将已经唱过的当前歌曲归档，尚未开唱的旧当前歌曲仍保留在待唱队列。历史不参与预处理排序、队列容量或缓存保护；再点仍通过标准 `POST /v1/room/entries`，创建新的队列条目并复用可用任务。

`POST /v1/room/entries` 也接受 `force: true`，与 URL 或任务 ID 一起使用时完整重做该视频，用于最终版本的整曲回归；普通点歌和失败重试默认复用缓存。此参数不改变房间队列容量。

任务 ID 表示重播选中的现有成品：文件完整就直接复用，不因服务升级重新处理。仅视频被回收时，仍用原音轨和字幕补视频；音频的 `pipeline_version` 保留，新的渲染版本单独记为 `presentation_pipeline_version`。URL 准备入口同样复用完整成品并保留原处理版本；显式 `force: true` 才重新准备。更新字幕时保留源文件及两次分离的检查点，解码后按输入、模型和代码哈希复用分离结果；其余可再生成的中间音频清理。历史中已经删除的检查点无法补认有效。

网页普通点歌额外传 `if_absent: true`：服务端按同源视频判重，已在待唱队列时不新增条目或重复启动处理；已知任务 ID 继续重播该成品，URL 准备入口按上述版本规则处理。该检查与入队在单服务事件循环内完成，两个客户端同时点同一首也只入队一次；不同来源的同名歌曲仍分别入队。「已唱 → 再点」传 `false`，允许主动重复演唱。省略该字段仍保留原 API 的重复入队行为。

`levels` 独立调整三个声部，支持部分更新，例如 `{ "action": "levels", "levels": { "backing_vocals": 0.35, "lead_vocals": 0.2 } }`。键为 `instrumental`、`backing_vocals`、`lead_vocals`，值为 0–1 的有限数。房间快照中的 `levels` 包含全部三个值，手动设置不对应预设时 `mix` 为 `custom`。切歌、暂停、定位不改变音量；选择 `mix` 预设则重置三个值。`storage` 随房间 SSE 快照推送，前端不轮询。

`pitch` 实时设置三轨共同的升降调，例如 `{ "action": "pitch", "pitch_semitones": -2 }`。接受 -6 至 +6 的整数半音数，0 为原调；兼容字段 `pitch_semitones` 持久保存；当前网页在本机保存，不同步到其他设备。此命令不改变播放位置、播放速度、音量、预处理结果或缓存音轨。

预处理队列按歌单中尚未开始的歌曲重新排序，不中断当前处理。播放抵达未准备好的歌曲时等待；旧服务端播放模式下，媒体加载完成后由客户端发送 `ready`，从设定位置起播，不把预处理／加载耗时算入歌曲时间。首个起音不足四秒的成品通过 `opening_countdown` 提供准备提示。零点起播时 `ready` 可返回未来的 `started_at`，播放器必须等到该时间再启动三轨和视频，并在等待期间显示倒计时；中途续播不加此等待。移除最后一个引用该任务的点歌项时，普通 worker 会停止尚未完成的整个进程组，并等待清理完成后返回；任务记为 `cancelled`，自动重试一并取消。完整成品继续保留并参与 LRU，不影响其他设备正在播放的成品。

取消后的已完成阶段检查点、来源文件和诊断仍保留在原缓存预算内，未完成阶段的临时文件清理。再次点歌会复用同一任务，逐阶段验证输入、模型、代码和产物哈希后继续；取消过程中重新点歌，先等待旧进程退出，随后只启动一次恢复任务。其他待唱条目仍引用同一任务时不取消，独立 probe 的生命周期仍由其控制器管理。

浏览器用同一个 Web Audio 时钟播放按需分段的 FLAC 音轨，MV 静音跟随。每个设备独立负责自己的声音与画面，旧的 `/?remote=1` 也正常播放。完整说明见 [APP.md](APP.md)。

### 分段播放

`GET /v1/jobs/{id}/playback` 返回音轨列表 `stems`、音轨组合版本 `version`，以及共有的 `sample_rate`、`channels`、`frames`、`chunk_frames`、`padding_frames`。网页从待唱项或曲库取得 `playback_version`，在播放清单和每个片段请求中传入 `?v=该版本`。任何音轨或共同增益更新后，旧版本请求返回 409。元数据查询不刷新 LRU。

`GET /v1/jobs/{id}/playback/{stem}/{chunk}` 返回单段 24-bit FLAC，`stem` 取自上述元数据的 `stems`，`chunk` 从零开始。两个请求都传入浏览器 AudioContext 的 `sample_rate`（默认 48000）。每段 8 秒，前后附加至少 20 ms 的重采样余量，边界同时落在源采样与浏览器采样的整数位置；按元数据裁掉重叠部分，并以整型源帧边界调度全部音轨。读取期间取得缓存租约，实际音频访问刷新 LRU（同一任务按一秒粒度合并持久化写入，活跃传输的租约仍逐个计数）；不写入新缓存文件，不触发预处理模型。

播放读取使用独立的八线程执行池。相同音频窗口共享一次编码和响应正文，服务端按 LRU 最多保留 512 MiB、256 个分片；这是进程内存缓存，不生成额外歌曲文件。任务状态、源文件身份及修改时间、共同增益和分片边界都会重新检查，文件变化、回收或重新准备后不能返回旧分片。等待和执行中的请求都持有缓存租约；HTTP 请求取消时，尚未开始的读取直接取消，已开始的读取完成后才释放租约。服务关闭会等待读取结束。租约计数与缓存回收在同一事件循环内修改。视频访问时间的数据库写入也放在线程池中，租约在等待写入前取得，写入失败或传输结束后释放。

内置服务入口的 HTTP 空闲连接保留 16 秒，覆盖两个音频分片周期，减少播放过程中反复建连及分片请求遇到空闲断连的竞争。另用 Uvicorn 或反向代理启动时，也应让连接保留时间覆盖分片请求间隔。

旧服务端播放接口接收 `buffering` 时要求携带 `entry_id`、共同的已播 `position` 和当前 `playback_started_at`。服务器拒绝切歌、定位、暂停之前的过期事件；有效请求保留播放意图并清空 `started_at`，直到片段齐备后收到带当前 `revision` 的 `ready`。

## 提交

```sh
curl -sS http://127.0.0.1:8746/v1/jobs \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://www.youtube.com/watch?v=n5sjpCQhTDk"}'
```

也支持 `youtu.be`、YouTube Music 单曲链接、YouTube shorts/live 的录播。一个任务只处理一个视频；直播流、播放列表和超过默认 15 分钟的视频会拒绝处理。

立即返回 HTTP 202：

```json
{
  "id": "任务 UUID",
  "status": "queued",
  "active_stages": [],
  "status_url": "http://127.0.0.1:8746/v1/jobs/任务UUID",
  "cache_hit": false
}
```

### 可选参数

| 字段 | 默认 | 用途 |
|---|---|---|
| `mv_audio` | `instrumental_backing` | 兼容旧请求的记录字段，不改变当前静音视频或网页混音；网页只调节主唱增益 |
| `lyrics` | 自动 | 字符串数组或按换行分句的文本；应与该视频版本实际演唱一致 |
| `language` | 自动 | ISO 语言代码或名称，如 `zh` / `ja` / `en` / `ko-KR` / `fr` / `ru` 或 `Chinese` / `Korean`；处理时按安装的 Whisper 模型能力解析 |
| `title`、`artist` | 自动 | 覆盖片头歌曲和原唱信息 |
| `force` | `false` | 强制创建新任务，不复用同链接、参数、流水线版本的任务 |

```json
{
  "url": "https://www.youtube.com/watch?v=n5sjpCQhTDk",
  "language": "zh"
}
```

## 查询和下载

```sh
curl -sS http://127.0.0.1:8746/v1/jobs/任务UUID
```

状态依次为 `queued`、`running`、`completed`；失败为 `failed`，通过 `error.code` 与 `error.message` 获取原因。`active_stages` 会显示当前正在下载、分离、整理歌词、对齐还是渲染。同一首歌的独立步骤可并行，因此可能同时显示两个阶段。

使用响应中的产物 URL 下载文件。URL 的 `v` 参数是该文件的 SHA-256；同任务修复后会变化，客户端不能只按任务 ID 复用旧媒体。版本 URL 支持私有缓存和 Range 请求；过期版本返回 409，避免把新文件片段拼进旧缓存。无版本的旧地址仍可用，但要求重新验证缓存。

已发表歌词开头的「歌名－歌手」与紧随的词曲署名单独移除，正文保留。只有歌名和歌手、没有歌词正文的响应不作为候选，继续尝试其他来源；所有来源均无正文时按缺少歌词失败处理。

在线歌词在对齐前检查明显残缺：按拉丁文字的词、其他文字的字计数，少于每十秒一个文本单元时跳过该候选，继续尝试同站其他匹配版本、备用查询和其他来源。重复唱词照常计数，换行数量不影响判断。同一录音的独立来源之间，某份文本不足另一份的一半、且至少 90% 都包含于后者时，也按歌词片段排除。拒绝原因、长度和来源保存在查询与交叉检查诊断中；全部候选被拒绝时标为 `lyrics_incomplete`，不进入对齐、不发布“已准备”。用户明确提供的歌词保持原文，准备阶段继续执行完整性与时间校验。

普通点歌与严格音频验收区分处理。普通点歌先查已发表的歌词文本，核对歌名、歌手与版本，再做声学对齐；该路径的 `validation_scope=playback_lyrics_first`。身份足够明确后，并行查询 LINE MUSIC、LRCLIB、网易云、LyricsWeb 和同一视频的 YouTube Music 歌词；已有视频简介歌词及后续查询到的日文注音歌词页也可作为候选。LRCLIB 候选另做时长检查。正文规范化后至少两个不同来源一致且无同票数冲突时优先采用一致版本，已知同一出版方去重；未达成一致时选用可信来源原文并保留冲突，不拼接歌词。`lyrics_provenance.lyric_lookup.crosscheck` 记录来源和比较结果，`lyric-crosscheck.json` 另保留各份候选文本。结果状态包括 `corroborated`、`conflicting`、`insufficient_sources`，`selection` 记录 `agreement` 或 `published_source`，后两种状态本身不阻止声学对齐。无可靠文本、全曲无可用字幕或仍有输入歌词行缺失时为 hard fail，保留音轨、可用字幕和诊断，不返回可唱成品或“已准备”。输入歌词完整但字词精度需要局部回退时，可返回 `completed`，`validation_scope=playback_with_lyrics_review`，`quality.playback_fallback` 保留错误与字幕模式，`lyrics_provenance.needs_review=true`。各句独立恢复，有效词字保留原时间；失败词组在已有词组起止点或相邻词组／唱句边界之间匀速扫亮。`timing_source=linear_fallback` 仅用于播放，内部记录 `estimated_spans`、`phrase_timing_sources` 和 `omitted_lines`，页面不额外显示估算标记。不能确定合法唱句时间时保留缺行诊断并阻止发布；不因其他行可用就把整首标为已准备。历史 ASR 草稿仅作诊断，不作为回退字幕。音轨分离、文件和完整解码失败仍然阻止发布。`--audio-only` 固定回归继续执行原有完整验收，任何这类回退都不能计为通过。

多首交错处理时，普通 worker 使用数据目录中的 `stage-locks/` 协调下载、分离、识别／对齐、音轨封装、视频渲染和封装；各类阶段按配置限制并发，不同阶段可交叠。首次下载和补视频共用下载阶段，避免突发请求和同时改写登录文件。`stage_progress.<阶段>.waiting=true` 表示尚未获得执行机会，等待不计入模型运行超时。任务结束或进程退出会释放阶段锁；共享缓存预算保持不变。

外部语音／歌词服务错误还包含 `error.provider` 和 `error.retryable`：超时、连接或限流可以退避后重试；内容拒绝、认证或权限失败需要人工处理。错误码分别为 `openai_timeout`、`openai_connection`、`openai_rate_limit`、`openai_content_rejected`、`openai_authentication` 和 `openai_permission`。对外只返回固定说明，不暴露原始响应、请求头或密钥；已完成阶段仍按检查点规则保留。

`stage_progress` 按阶段提供实测计数，例如 `{"separate_music":{"completed":12,"total":40,"unit":"chunks","detail":null}}`。下载按视频／音频分别计字节，分离计已处理音频块，对齐计已处理段落／行，渲染计已送入编码器的帧。`total` 缺失时不计算百分比；加载模型、在线歌词请求、封装与校验仅提供阶段或 `detail`。这些是当前步骤的工作量，不能相加当作整首歌的时间百分比。只有成品通过校验后才会进入 `completed`。

语音识别出现局部长串重复循环时，先用前后有辨识度的歌词包住异常段，最多重识别 90 秒音频。新结果必须在原位置匹配两端歌词（文本相似度至少 80%、起止相差不超过 2 秒），只替换两个边界之间的文字与实测词时间；拼接结果仍须通过完整异常检查。局部恢复不可用时，依次用已有本地模型检查同一录音的原始混音和主唱轨，保留语言、录音时长、时间顺序与异常文本校验；恢复依据及拒绝原因写入 `asr/original-recovery.json`、`asr/lead-recovery.json`。主唱分离在识别前完成，封装与重采样仍可和分离并行；主唱输入变化会使相关识别缓存失效。仅这些本地候选仍不可用时，再用 `gpt-4o-transcribe` 在整首上下文中恢复歌词文本（可用 `KARAOKE_ASR_FALLBACK_MODEL` 配置），同时把 Whisper 的粗定位改为 30 秒片段、最多 3 路并发；仍循环的片段不提供词时间。恢复文本不带词时间，`recording_bounds` 只是录音范围，后续仍由声学强制对齐生成起唱时间。恢复过程记录在 `asr/run.json`，局部候选保存在 `asr/loop-repair.json`，持续异常会明确失败。这些边界检查不代表逐字起音准确率。

每次转录 API 的原始回包独立缓存在任务目录 `asr-requests/`，包括未通过校验的回包；按音频哈希、请求参数、请求实现及回包哈希校验后复用。后续文字处理失败不会重新请求相同音频，修改局部拼接算法也不丢弃已有回包。它们和其他阶段产物一起计入缓存预算，可由正常 LRU 回收；歌词、粗定位和日志也保留供复现。

歌曲信息提取的成功结果另存为 `song-metadata.json`，按输入视频信息、模型、实现和结果哈希检查复用。重做转录或修改对齐代码不会重新选择歌手名称或简介中的歌词行；新的转录仍正常参与歌词校验。输入、模型或结果文件改变时才重新提取，保留视频信息中提供的原文歌手名，避免仅用转写名称检索到不同歌词来源。

日文粗定位先按原文匹配。汉字与假名写法不同而未定位的连续句段，再用现有日文发音字典匹配；只使用前后已定位句之间的 ASR 词，不移动已有句子，也不改变歌词或生成时间。恢复的锚点标记 `match_basis: pronunciation_recovery`。缺词及遗漏唱段仍须通过原有整曲检查；读音匹配本身不代表逐字起音准确率。

只有标点的转录也会触发恢复；跨多段重复同一句且过半片段时间塌缩的结果视为解码异常。局部连续片段均不超过 25 ms、间隔不超过 25 ms、相同内容至少重复 8 次，也触发恢复，避免正常段落掩盖局部解码循环；正常计时的副歌和间隔开的短音节不受这条规则影响。自动语言请求在恢复时重新识别语言，不固定使用异常转录的语言标签；按可用分段词数中的字符量汇总语言证据，写入 `recovery.language_evidence`。用户显式指定的语言仍然保留。这些仅是恢复触发条件，不等于歌词准确率。

句子或词时间戳倒序、负数、非有限数或起止颠倒也会触发恢复，避免错误粗定位把多句歌词挤进很短的音频窗口。分段重试仍有这些问题时，舍弃该段的词时间并保留诊断；不排序、平移或钳制时间戳来伪造可用结果。

同一时刻堆积至少 8 个含文字的零时长词单元，也会触发重识别。少量零时长子词仍交给后续声学对齐；该阈值只用于决定是否重识别，不表示这些词一定没唱，也不据此删词或放宽最终校验。

流畅的短句也可能是前奏／尾奏上的幻听。若 ASR 的无语音概率至少 0.6，且该段至少三个词单元中有一半时间塌缩，或整段被压到 0.2 秒以内，也进入独立重识别。无语音概率本身不触发删词；有正常词时间的轻声演唱仍保留。这是复核触发条件，不是歌词正确性的证明。

语言标签按 ISO 名称和代码统一解析，不把中日英以外的语言当成无效结果。缺失或无效标签仍进入有上限的恢复流程；Whisper 调用按安装版本的语言表选择代码，不根据歌名强制猜测，也不默认改成英文。

恢复过程中，30 秒窗口仍无法提供有效词时间时，仅将该窗口分成最多两个不超过 15 秒的片段再试一次；不足 30 秒的尾窗均衡拆分，正常窗口不重跑。完整歌词继续使用整曲识别文本，短片段只补充真实识别得到的词时间，不拼接片段文本。仍异常的片段保留诊断、舍弃词时间，歌词匹配及最终对齐门槛不变。

本地恢复使用自动语言时，超过 30 秒的录音在四分之一、二分之一和四分之三处分别检查一个最长 30 秒的窗口，按多数一致的语种识别整曲，避免仅凭前奏判定语言。短录音使用完整片段，显式指定的语言保持不变。窗口分歧时缓存诊断并拒绝该本地候选，继续原有后备路径；不会退回前奏的猜测。窗口与语言概率保留在 `language_detection` 中。

整曲恢复文本的文字单元不足分段词结果的一半时，不能直接当作完整歌词。若初始整曲文本没有循环，且与分段词结果双向匹配均至少 55%，则复用初始文本，继续使用有效的分段词时间；不恢复初始异常时间戳，也不补写歌词。否则失败并保留词结果。选择依据写入 `asr/text-selection.json` 和 `recovery.text_selection`。

复用初始文本时，若文字与原始段落完全一致，保留原始文字分段供数字静音过滤使用，避免整曲合并后掩盖尾奏中的幻听；粗定位仍使用恢复后的词时间。若视频简介候选在复核后仍不匹配音频，仅在整曲 ASR 文本与独立分段识别双向匹配均达到 55% 时，才改用这份 ASR 草稿。拒绝的简介、匹配率及来源保存在歌词 provenance 中；用户提供或已核对的歌词不走此回退，后续字幕校验仍全部执行。

歌词与 ASR 词序列的粗匹配先最小化文字编辑距离，再在同分结果中选择歌词内部跳过片段更少的匹配；开头和结尾的非歌词片段不计入内部跳段，避免把对白里零散的字母拼成一句歌词。时间仍直接来自被匹配的 ASR 词，整体及逐句匹配门槛不变。该步骤使用固定版本的 Biopython 全局序列对齐器。

歌词来自用户、已核对目录或视频简介时，重识别前后的粗定位都可作为候选。原始候选必须语言匹配、词时间有效且顺序正常；选择整套文本匹配更好的候选，不拼造时间、不改歌词。选用来源和两套覆盖率记录在 `asr/filtered.json`，后续声学对齐和最终质量门槛不变。纯 ASR 草稿不靠原始转录自我验证。

上述歌词的粗匹配仍不足时，最多补识别三次：从未匹配段前后的有效锚点选取上下文，每段不超过 45 秒。上下文过长时缩至最近的相邻句，仍过长则检查边缘窗口；人声窗口不能改善匹配时，可检查同一时间范围的原始混音。经过独立分段重识别的 ASR 草稿也可走此流程。ASR 只接收音频和已确认的语言，不接收目标歌词；只拒绝局部异常的词时间，剩余结果仍须通过完整异常检查。仅采用提升整体匹配、时间顺序有效的词结果，保留窗口外侧的原词时间和全部歌词文本。每个窗口及音频来源有独立的输入、代码和结果检查点；诊断保存在 `asr/anchor-recovery.json`。补识别后仍使用原来的匹配门槛，失败则停止。

分块对齐遇到跨窗口冲突时，检查已有上下文预测，优先采用同一窗口覆盖相邻两句的结果，也允许采用其他重叠窗口里的完整单句。只有冲突减少且没有新增词起点、句尾顺序或过度重叠问题时才采用。这里复用后续字幕行校验，不通过移动时间戳修补；找不到合法候选时保留失败。

若对齐器返回的词与输入歌词不一致，对同一音频窗口只重试一次：关闭句间停顿填充并动态选择注意力头。候选须逐句完整覆盖原歌词，全部词都有有限、正时长、顺序正确的声学时间，且通过原有行时间校验才可采用；不删除重复词、不补时间。两次结果保存在 `alignment/raw.json` 的 `text_recovery` 中。原始结果在拼接校验前落盘，失败后也能复现；此检查不代表人工起音准确率。

整行仍没有时间时，再用相邻一句有粗定位的歌词扩充上下文，进行一次不限制单词时长的声学重试。它针对长哼唱被语音模型的时长限制截断、或孤立粗定位选错演唱位置的情况；只有全部文字和词时间通过原有完整性、顺序及范围检查才采用，原结果和候选保存在 `unresolved_recovery`。英文音素输入保留连字符，避免连续元音被误读成带额外辅音的单词；纯 `Mmm` 哼唱使用持续的 /m/，不按多个字母名称发音。

连续重复唱句只有最后一遍没有时间时，检查已定位唱句之间最大的空档。分别对空档及前后唱句的上下文做声学复核，窗口不超过 45 秒；候选的全部词必须落在空档内，至少一半且不少于两个相邻词的起点须在两次预测中相差不超过 200 ms，贴住裁剪边缘的词不作佐证。通过才将真实预测插回原顺序，保留全部歌词，其余词时间不动；原始预测和复核结果保存在 `alignment/raw.json` 的 `repeat_recoveries` 中。仍须通过后续音素对齐和全部输出校验。

映射显示文字时保留词间标点，包括模型拆开的英文缩写中的撇号；显示范围调整不改变音频测得的词起点，缺失的正文仍会被完整性检查拒绝。

分行产生的独立引号、句号等纯标点行并回相邻歌词，保留所有非空白字符及原顺序；开头标点随第一句显示。自动转录、视频简介和用户歌词采用相同处理，纯标点输入仍拒绝。对齐拼接也拒绝没有可唱文字的独立行，避免跳行后把下一句错误配给两个行号。英文音素对齐使用与词起点评测相同的词筛选方式，独立省略号等不作为发音词元；这些标点留在相邻词的显示范围内，不新增或改动起音时间。

英文默认保留整曲声学对齐，但用已通过顺序校验的 Whisper 唱句建立上下文范围。词时间跑到所属上下文之外时，仅对受影响的整块重新做声学对齐；重试在原窗口前后各多包含一句，避免粗定位裁断长音或混淆相似的哼唱。保留原词序和其他块的结果，不把词时间直接改成范围边界或粗定位时间。原范围、实际重试范围、预测及采用情况写入 `english-onsets/run.json` 的 `context_retries`。重算仍越界或出现顺序冲突则失败；最终音频验收也检查完整的 `english_context_scope`，不能仅凭文件、哈希和时间单调计为通过。

重复唱句的音频匹配若因时长差异或无效特征找不到合法路径，只拒绝该候选并记录原因，继续检查其他参考句；没有可用候选时保留此前的时间，仍须通过后续字幕校验，不放宽匹配路径或最终门槛。

合并的中文字组若仍无法拆开，会检查相邻歌词的中文上下文，裁掉英文等非中文唱词及对应音频，防止中文音素被强行对齐到英文。旧的相邻字边界挡住候选起点时，可以将这些相邻字一并重新对齐，但每个改动的字都必须通过同样的三个声学窗口及原音／人声双视图复核，不能直接挪开旧边界。窗口超过 30 秒、裁剪后不足三个不同窗口或无法获得独立证据时保留失败。

同曲重复唱句也可提供拆字依据：仅使用已通过跨模型复核的参考字；分别计算原音和人声的音高、频谱四条匹配路径，沿用已有重复唱句的路径代价和一致性检查。映射出的目标起点还必须得到目标原音和人声的独立声学复核，并有可听音频及合法的相邻字范围；不直接复制副歌间的固定偏移。过程及拒绝原因写入 `context/song/verified-repairs.json`。

残余字组可再用可选 Qwen3 ForcedAligner 的原音／人声双视图复核；仍要求 SOFA 三个上下文的起点稳定、两份独立预测均在 100 ms 内、正时长、可听声音及合法顺序。Qwen 只提供独立证据，不直接替换主对齐时间；SDK 的插值及时间修补关闭，原始异常时间会被拒绝。依赖在子进程隔离，诊断见 `qwen-witnesses.json` 与 `qwen.log`，模型和配置变化只使相关对齐缓存失效。校准范围见[自动检查说明](docs/automatic-quality.md)。

中日文歌曲里的英文段若仍有多个词合并高亮或单词被拆断，会用现有英文 SOFA 模型在三个上下文重新对齐，并用 MMS 分别核对原音与分离人声。单词跨越多个字幕单元时，先扩展到完整单词覆盖的单元，再用新的声学预测取起点；范围若涉及未分开的中日文字或已核验的重复片段，保留原结果。混合语言句只截取已有字词边界限定的连续英文段，两种模型和两份音频都受相邻外文的时间边界约束；无法取得三个不同窗口时保留失败。沿用 80 ms 的上下文极差、100 ms 的独立模型差异及原有音量、邻词范围和顺序检查；不满足就保留原结果及失败。只替换证据完整的缺失高亮范围，其余词和相邻中日文保持不变，诊断见 `context/song/latin-repairs.json`。

固定样本回归控制器 `karaoke.tools.soak` 会把各阶段日志末尾最多 16 KiB、轻量对齐诊断及 ASR 原始响应压缩保存到 `service-data/soak-100/`，其中每份 JSON 最多 16 MiB。被拒绝的恢复响应、最终字幕和产物清单也会保留；最终字幕的覆盖检查结果及其输入哈希写入 `lyric-coverage-validation.json`，一同归档，便于在任务缓存被 LRU 回收后复查拒绝原因。归档按诊断内容的 SHA-256 区分，同一任务再次报相同错误时也不会覆盖早先的证据；归档仅包含轻量诊断。

控制器将 DNS 解析失败归为网络故障并退避，不等待代码版本变化才允许重试。同一平台的新退避只延长已有等待，不会让后来的短等待覆盖先前的长等待。服务主动关闭或 macOS 明确报告正在关机时，保留原始错误和阶段检查点，短暂等待后允许同版本重试；这类本机中断不触发视频站点或 OpenAI 的全局退避。普通模块加载错误仍按软件故障处理。

失败任务中已经验证完整的视频下载也暂存于同一缓存预算内。重试相同 URL 时先核对文件 SHA-256，再复用本地视频，避免重复下载触发站点限制；这些原视频同样优先参与 LRU 回收。`force: true` 不复用失败任务的下载。

失败后的普通重试也复用逐阶段检查点：解码、两次分离、双轨／三轨封装、ASR、歌词整理、各步对齐和渲染分别保存输入、配置、相关代码与产物指纹。同一请求可在原任务 ID 上重新排队，`attempt_count` 增加；校验通过的阶段跳过，失败或已损坏的阶段重跑。改变对齐代码不会使音乐分离失效；下游通过实际输入内容决定是否失效。成功只在输出完整并通过校验后记录，半成品不会作为检查点。结果的 `reused_stages` 列出复用步骤。

对齐阶段只跟踪自己使用的模型：粗对齐跟踪 Whisper，音素、重复句和上下文对齐跟踪当前语言的 SOFA。新增未启用的实验模型不会使生产版本或已有对齐缓存失效；更新其他语言的生产模型会更新整体版本，但不会重算当前语言的无关阶段。

检查点和中间音频与成品使用同一缓存预算；失败时保留已完成阶段及 JSON 诊断，成功后只保留最终产物。LRU 仍可回收未受保护的失败任务，所以断点恢复以文件尚未被回收为前提；不会为了保留检查点提高 10 GiB 上限。`force: true` 始终重新完整处理。

房间快照也包含每首运行任务的 `stage_progress`，通过 SSE 更新。进度来自子进程的结构化标准输出；计数更新通常限频为每 0.5 秒一次，阶段切换立即推送。前端不轮询，不根据经过的时间伪造进度。

曲库从入队开始就包含歌曲，状态可以是 `queued`、`running`、`completed`、`failed`、`cancelled`、`video_evicted` 或 `evicted`；静态目录中尚未提交的歌曲为 `unprepared`。同一视频优先展示文件完整的成品，其次是可补视频的任务，再按创建时间选择；较新的失败记录不会遮住可播放成品。`job_id` 也可指向尚未完成的任务，再次点播时复用该任务，不重复下载或处理；只有 `status == "completed"` 才表示已准备好。房间 SSE 快照的 `library` 与 `GET /v1/library` 使用同一份数据，元数据、语言分类和进度一并推送。

页面语言分类优先采用用户指定值，再使用已生成结果、当前音频语言信息或已知曲目目录。处理初期可用所选音频轨的语言标签暂时分类，ASR 返回后立即更新，歌词整理后再次确认。未知语言暂时只列在「全部」，不会按标题文字或字幕语言猜测演唱语言。

取得下载元数据后，`song_info` 立即提供 `title`、`artist`、`duration_seconds`，并通过房间 SSE 更新歌单，不必等整首准备完成。优先使用视频的音乐标签，否则先显示视频标题；不把上传者当成原唱。歌词整理完成后再更新歌曲信息，用户填写的歌名／歌手始终优先。`input` 保持原请求，`result` 仍只在成品完成后提供。

LRU 先清理未受保护任务的无用中间文件，再回收视频：任务为 `video_evicted`、`restore_video: true`，仅 MV 接口返回 HTTP 410，其余音轨、字幕和封面仍可获取。提交相同输入（`force: false`）或用原 `job_id` 点歌，会复用原任务进入 `queued` / `running`，只下载、核对源音频指纹、重新合成视频；不会重跑模型。完整 `audio_ready` 任务首次补视频也走同一路径。恢复沿用原先算好的结果，即使渲染器版本更新；成功后清除 `restore_video`，恢复耗时单列在 `result.video_restore`。恢复失败保留产物，房间的 `retry` 仍只补视频。源音频指纹不同报 `verify_video_failed`，可用 `force: true` 显式完整重做。

视频回收后仍空间不足，才完整回收任务为 `evicted`，全部原文件接口返回 HTTP 410。重新提交同链接或用原 `job_id` 点歌会完整准备。缓存不足导致准备中断时错误码为 `cache_full`；不会删除待唱歌曲来掩盖空间不足。默认上限、统计范围和运行中写入限制见 [缓存说明](APP.md#本地缓存上限)。

完成后的 `result.artifacts` 每项包含 `url`、`bytes`、`sha256`：

| 名称 | 文件 |
|---|---|
| `mv` | 已烧录字幕的完整 MP4，含静音 AAC 兼容轨；音乐由独立音轨播放 |
| `accompaniment` | 普通播放的底轨 FLAC，包含背景音乐＋伴唱 |
| `instrumental` | 严格三轨验收的背景音乐无损音轨 |
| `backing_vocals` | 严格三轨验收的伴唱无损音轨 |
| `lead_vocals` | 主唱无损音轨 |
| `instrumental_preview` | 背景音乐 MP3；仅旧任务或严格音频验收 |
| `backing_vocals_preview` | 伴唱 MP3；仅旧任务或严格音频验收 |
| `lead_vocals_preview` | 主唱 MP3；仅旧任务或严格音频验收 |
| `subtitles` | 包含逐字／词时间的 JSON |
| `poster` | 可选的本地 JPEG 封面：优先视频缩略图，获取失败时截取 MV 画面 |

文件接口支持 HTTP Range，可直接交给播放器或下载。处理完成前访问文件返回 409；未发布的内部文件无法通过文件接口读取。

```python
import time
import httpx

base = 'http://127.0.0.1:8746'
with httpx.Client(timeout=30) as client:
    response = client.post(base + '/v1/jobs', json={'url': 'https://www.youtube.com/watch?v=n5sjpCQhTDk'})
    response.raise_for_status()
    job = response.json()
    while job['status'] in ('queued', 'running'):
        time.sleep(2)
        response = client.get(job['status_url'])
        response.raise_for_status()
        job = response.json()
    if job['status'] != 'completed':
        raise RuntimeError(job['error'])
    for name, artifact in job['result']['artifacts'].items():
        print(name, artifact['url'])
```

`GET /v1/jobs?limit=20` 列出近期任务；`GET /health` 返回队列和正在处理的任务。持久退避记录或任务读取失败时，调度器保留对应任务、继续处理其他可运行任务；健康状态为 `degraded`，`dispatch_blocked_jobs` 列出受影响的任务 ID。损坏记录不按零退避处理，修复记录后自动继续。单条无效进度消息记入日志，不终止计算；最终产物校验仍照常执行。

## 严格音频验收的 ASR 与质量边界

以下描述 `--audio-only` 的独立验收路径。普通点歌使用前述已发表歌词优先流程；找不到可靠文本时失败，不使用 ASR 草稿替代歌词。

已核对的本地歌词只在视频身份和时长匹配时复用。新视频从分离人声生成 ASR，按原文顺序分行，仅改变空白，不让文本模型增删歌词、重复句或改写唱词。结果标为 `asr_draft` / `needs_review`，附转录指纹；复核时关注识别错字、对白和幻听。文本和词时间支持不足、粗时间轴冲突或字体缺字时仍明确失败，可提供修正后的 `lyrics` 再提交。文字来自 ASR 时，文字匹配率用于一致性检查。

分离人声的转录异常且局部恢复未解决时，先用已安装的 `large-v3-turbo` 识别同一录音的原混音，再考虑整曲在线重试。两份音频的时长必须一致；自动语言请求重新检测语言，显式指定的语言必须匹配。仍有重复、塌缩时间、越界或缺失词时间的候选不会采用。原始响应按音频、模型和代码缓存，选择理由保存在 `asr/original-recovery.json`，原混音也参与阶段缓存签名；此步骤只恢复 ASR 草稿，后续歌词和逐字对齐检查保持不变。

局部重识别覆盖重复循环，以及同时出现无声警告和词时间塌缩、整句词时间重合的异常片段。中间异常若带有解码窗口 `seek`，同一窗口内的其他句子也不能作为可靠拼接边界，改从窗口外选择锚点；缺少窗口信息时保留原有选择方式。中间片段仍须匹配前后唱句，保留片段外的原词时间，并对拼接后的完整转录重新执行质量检查；没有可靠前后边界或超过 90 秒就不拼接。诊断保留触发片段索引及窗口标识，不按文字内容删除疑似幻听。

转录语言采用用户显式指定值；未指定时从音频自动检测。下载器提供的音轨语言标签可能不准确，只用于页面暂时分类，不限制识别语种。标题文字和字幕语种同样不作为转录语言。

两份整曲转录都无法提供完整歌词时，保留独立分段识别的词时间，将转录正文留空，再检查用户歌词、已核对目录或视频简介中的原文。只有独立歌词通过原来的音频匹配和后续对齐检查才能继续；没有独立歌词或内容不匹配仍会失败。被拒绝的转录保留在诊断文件中，不用它补字、拼接歌词或生成时间。

文本模型整理标题、音乐标签和上传者字段；视频简介含完整歌词时，它只返回所选原文的行号，代码检查范围、顺序和重复行号后提取原文，不让模型生成或改写歌词。保留原文分句，不按固定字数另拆对齐行，以免将日文词尾或英文末词孤立成行；独立标点仍并入相邻句，原有单行长度限制仍生效。保留简介指纹和行号，来源标为 `video_description`；这些歌词仍经过同一套音频匹配与对齐门槛。简介没有完整歌词或行号无效时使用 ASR 草稿。歌曲信息请求失败时保留视频标签和标题，并将原因记录在 `lyrics_provenance.metadata_error`；不会反复提交被拒绝的内容。ASR 阶段的错误仍正常报错和退避。

同一 YouTube 视频若提供与演唱语言一致的人工字幕轨，可用其文本替代 ASR 草稿。排除自动字幕、自动翻译和其他视频的轨道；文本与音频转录的双向支持均达到 55% 才采用，来源记为 `source_manual_subtitles`。保留原文和重复句，字幕的显示时间仅用于检查文件范围，不作为逐字起音时间；后续声学对齐及质量检查不变。原始响应单独缓存为 `source-captions.json`，临时错误按服务端提示或至少五分钟退避；取不到字幕时保留 ASR 路径。404、429 等字幕请求错误保存在诊断的 `error` 字段，不中断后续歌词查找和原有质量检查；缓存命中时也保留错误和退避时间。

仍只有 ASR 草稿时，可从 [LRCLIB](https://lrclib.net/docs) 检索独立歌词文本。先要求歌名、歌手相符（允许繁简体及中英双语名称中的中文别名），版本标签不作为别名删除；录音时长误差不得超过 2%，容差下限 3 秒、上限 10 秒。然后沿用双向 55% 音频文字支持门槛，保留原文和重复句，来源记为 `online_lyric_text`。只使用纯文本，完全不采用歌词站的时间戳；逐字时间仍由本视频的音频对齐、复核，所有后续检查不变。响应及错误缓存在 `lyric-lookup.json`，临时错误遵循至少五分钟及服务端 `Retry-After`；查不到、版本不符或网络不可用时保留 ASR 路径。此项是新歌的在线检索，不依赖被 `KARAOKE_DISABLE_LYRIC_CATALOG=1` 禁用的开发歌曲本地歌词库。它不替换用户提供、已核对或来自视频本身的歌词。

视频容器若在原音频首尾填充了全零静音，整体时长匹配失败后会按原始 PCM 的非零内容时长再用同一容差比较。只有所有声道都严格为零的首尾可排除，微弱声音仍计入；全静音、非有限采样或与源时长不符的文件不提供此依据。音频文件、帧数和字幕时间轴保留不变，匹配依据及源文件哈希记在 `lyric_lookup.duration_basis`。

歌名末尾括号中的明确影视用途说明（例如 `电影《片名》主题曲`）可以作为歌名别名处理。只识别这类完整说明，不泛化删除括号；现场版、混音版、语言版本及其他限定继续参与匹配，歌手、时长和音频文字支持检查不变。回放失败样本时须保留正式流程实际产出的短歌名和歌手，不能预先改成歌词库的标题再宣称验证通过。

原视频标题明确写有 `Live from/at/in 场地` 时，歌词候选的曲名或专辑必须标明同一场地；不会因文本模型缩短了歌名就丢掉这项约束。其他现场或没有场次信息的歌词不采用，继续检查本录音的 ASR 草稿；仍保留完整性和对齐门槛。

简介省略重复副歌时，用已有 ASR 检查唱句间未覆盖的音频：至少 24 个文本单元、连续两行原歌词与转录相似度达到 90%，首尾均有粗定位支持，才可复制该原文段落。多解、原唱句被移到另一遍、插入句超出空档均拒绝；用户歌词和已核对目录不自动增补。原文、词时间和复制范围保存在 `asr/lyric-repeats.json`，不新增下载或 ASR 请求。增补后仍做正常声学对齐；最终流程及音频验收再次检查是否遗漏已识别的重复段。此项检查覆盖已有转录证据的漏段。

另外反向检查整首识别结果是否被歌词覆盖，防止简介只引用结尾几句却因匹配率高而通过。先完成有证据的副歌增补，再检查至少 55% 的识别单元能按序匹配，且字幕前、后、句间没有整段未覆盖的识别内容（沿用至少 24 单元的唱段门槛）。检查使用完整恢复词流，不因选择了另一套粗定位而丢掉已识别的唱段。简介摘录仅在完整 ASR 文本获得独立词流支持时回退；用户歌词不改写。诊断保存在 `lyric-repeats.json` 的 `lyric_coverage`，最终产物验收会重新计算。这是漏段检查，短即兴词、未识别出的歌词和毫秒起音精度仍不由它证明。

### 当前播放策略的一次性回归

`karaoke.pipeline --playback-audio` 只导出音轨与字幕，但使用普通点歌的可信歌词查询、并行阶段和局部字幕回退，不运行旧 `--audio-only` 的独立 ASR 验收。文件哈希、格式、完整解码和字幕时间范围仍需通过。字幕降级可完成音频产物，但不算严格逐字准确率通过。

跨机器执行时，可用 `--prepared-lyrics FILE` 读取由同一 `prepare_online_lyrics` 查询生成的结果；包中须保存 `prepared_lyrics_identity(url, metadata)`、查询结果 `lyrics` 和来源信息。源元数据、查询代码或歌词来源不符会拒绝使用，不在 GPU 机器重新查询。凭据不属于该文件。

`python -m karaoke.tools.playback_sweep --manifest MANIFEST --data-dir DATA --report REPORT --prepared-dir INPUTS` 对固定清单每首只提交一次，使用 `run_probe` 的锁和共享缓存监控。普通 worker 必须暂停；控制器复用已有来源和有效的音频阶段检查点，保留用户歌单；已有完整 MV 时另建音频任务，避免覆盖。每首结果写入独立报告的 `audio_attempts`，不会改写原固定清单或历史严格音频／MV 账本。

加 `--concurrency 2` 可同时推进多首歌曲的计算和最终校验；默认仍为 1。整个批次持有同一个 `run_probe` 单实例锁，各首共用原有阶段资源锁和服务配置的缓存预算（默认 10 GiB，可取消应用配额，始终检查实际磁盘余量）。按本地源音频的帧数、采样率和声道预留工作文件空间，优先调度按清单顺序第一个已备好歌词且能放下的样本；长歌暂时放不下时，后面的短歌可以先填空档，报告顺序保持不变。所有样本都放不下时才等待当前歌曲释放空间；容量未知时单首执行。单曲软件失败保留诊断后继续；缓存、服务或版本异常会停止接收新任务并终止本批次处理进程。控制器与所有歌曲共用每秒一次的缓存／健康快照，避免每首歌重复扫描整个共享缓存；入场空间预留和完成验收强制刷新。控制器与子任务的监控请求偶发连接中断时记录原因，等待 0.2 秒后重试一次；再次失败仍停止整批，已确认的空间不足不会延后处理。报告旁的 `.pause` 只停止接收新任务，已经开始的歌曲自然完成。并发不会改变模型 batch、精度、歌词、校验门槛或固定清单顺序。报告记录并发上限和每首含校验的墙钟时间，模型阶段耗时仍单独保留。

- `clean`：音轨、字幕产物通过本轮检查，没有记录到回退。
- `soft_fail`：产物可用，但歌词来源存在文本分歧、单个来源请求失败，或字幕对齐／高亮采用了回退；保留原因、来源与局部回退数量；仍有缺失行时处理失败。仅未找到第二份来源不算请求失败。
- `hard_fail`：处理终止或产物完整性检查失败。
- 同一首可在硬失败前出现软失败，因此软失败事件数与歌曲数分别报告。

恢复控制器时跳过所有已有尝试；未结束的尝试必须先核对，不自动重跑。`REPORT` 同名的 `.pause` 文件在歌曲之间暂停。每首歌词文件以 URL 的 SHA-256 命名；未到达时等待，因此本机查询和 GPU 处理可以重叠进行。此回归不验证 MV 渲染、播放器或独立人工起音精度。

### 先验证音频

定位失败歌曲时，可在同一个任务目录运行 `python -m karaoke.pipeline --request REQUEST.json --output JOB_DIR --audio-only`。该模式只请求音频流，执行同一套解码、两次分离、精确封装、转录、歌词及逐字对齐，输出 `audio-result.json` 和七项音频／字幕产物，不生成 `result.json` 或 MV，也不能计为整曲 MV 回归通过。用 `karaoke.tools.soak.verify_outputs(..., audio_only=True)` 校验母版重组、文件哈希、全部 MP3 解码和字幕完整性。

共享服务上的测试用 `python -m karaoke.tools.soak probe --manifest MANIFEST.json --data-dir DATA_DIR --job-id JOB_ID`。先暂停批量控制器及预处理 worker，并通过普通点歌接口注册任务；该命令检查来源退避和 worker 暂停状态，使用服务的缓存回收接口监测共享预算，超限时终止本次测试并保留检查点。它不会启动其他样本或将音频通过记作 MV 通过。

交互式修复可以向 `run_probe` 传入自己创建的暂停文件原文 `resume_preparation`：在暂停期间认领已注册任务，然后恢复普通调度，与新点歌曲共用阶段锁和缓存预算。进度仍由子进程标准输出推送；修复控制器负责验证成品后发布结果。外部控制器写入本地任务库后可调用 `POST /v1/room/events` 通知 SSE 更新，该接口不接受或修改任务结果。严格音频验收默认继续独占，不能使用此选项改变验收口径。

重试按失败原因计时：OpenAI 暂时性错误从 30 秒起退避，保留 `Retry-After` 或响应中的重试时间，不能早于服务端要求；请求过大、额度不足和鉴权问题等待配置修复。限流按模型隔离，可选元数据模型的额度不阻塞 ASR。后台验收的视频 DNS／超时从 60 秒起、单个资源的 403 从 5 分钟起退避，均不冻结整个视频来源；429 才记录来源限流，登录验证和不可访问的视频停止自动重试。已有明确限流期限不会因另一次失败而缩短。

普通点歌 worker 对 `download_failed`、`download_video_failed` 使用同一错误分类，最多自动重试三次。为缩短开唱等待，非限流的临时下载失败（包括单资源 403）三次分别等待 5、20、80 秒；仍遵守更晚的服务端 `Retry-After`，429 保留来源级退避。这个交互式等待策略由 API 调度层负责，不改变音频算法指纹和已有成品缓存。等待重试的任务保持 `queued`，通过 `download_retry` 保存次数、下一次 Unix 秒时间、来源退避和安全错误历史，原始诊断追加到本机 `download-retries.log`；房间快照提供 `next_retry_at`。退避不占用执行名额，重启服务后继续原期限，已校验的阶段和同一任务 ID 保留。显式 429 期限同时持久化到共享工位目录，下载子进程在取工位前检查，避免并行流水绕过退避。最后一个待唱引用被移除时取消后续自动重试。耗尽重试或遇到登录、不可访问、配置错误才保持 `failed`；手动重试重新获得次数，但仍遵守来源退避。ASR、字幕校验、空间不足等其他失败不在此自动重试范围内。

同一次下载先报 429、随后要求登录时，两种限制同时保留：该歌曲继续等待登录问题解决，同一来源的其他下载也须遵守 429 退避；不会因最后一条登录提示而漏掉前面的限流。

单首 `probe` 同时检查整曲任务记录、音频任务记录和来源退避，以最晚的截止时间为准。音频刚失败时，即使整曲记录没有等待期限，也不会立即再次下载或调用模型；退避拦截不改动已有阶段产物。

歌词粗定位缺失时，局部补识别也覆盖整首开头和结尾：缺口由已有唱句与录音首尾限定，再截取不超过 45 秒的片段。录音边界不作为歌词起止时间；候选必须提供有效的实际词时间并改善原有文字支持。整首没有任何可用锚点时仍失败，不猜测唱句位置。

固定样本音频回归使用 `python -m karaoke.tools.soak audio-run --manifest MANIFEST.json --data-dir DATA_DIR`。逐首验证七项音频／字幕产物，遇到软件失败立即停下供修复；结果单独写入 `audio_attempts`，仅统计同一实际 pipeline 版本。`audio.pause` 可在当前首完成后暂停。通过的任务记为 `audio_ready`，移除本控制器加入的待唱条目，释放缓存保护；完整音轨与字幕保留，清理无用中间文件。它没有完整 MV，因此网页仍显示未准备，后续点播仅补视频。旧 worker 队列中的此类条目不会擅自重跑。

先处理已有音频失败和其他已到重试时间的历史失败，再处理未完成样本；旧版本已通过样本的复验排在最后，避免延迟修复效果的验证。外部失败在到期后按最久未尝试的顺序重试，避免刚超时的请求连续抢占其他失败样本。尚处于退避期的外部失败不阻挡其他可运行样本。

需要只复测固定清单内的一首时，在 `audio-run` 后加 `--case-url VIDEO_URL`。它保留批量暂停文件，仅注册、处理和验证指定来源，使用同一个缓存预算与结果账本，完成后退出；已有运行任务、同版本未修复失败或来源退避仍会阻止重复运行。这样不必先恢复整批队列再抢时机暂停。

明确决定暂缓某个难例、先检查其余样本时，可用 `audio-run --defer-url VIDEO_URL`，支持重复指定。暂缓来源仍保留在固定清单及失败记录中，不计通过；其余样本仍在新的软件失败处停下。暂缓列表写入 `audio_deferred_urls`，全部通过的分母始终是原完整清单。该模式仍遵守 `audio.pause`。

需要先摸清整批失败范围时，加 `--keep-going`：单首处理或产物校验失败后保留失败状态与诊断，继续其他样本。同版本软件失败不会再次提交；同版本外部错误的重试排在其余可运行样本之后，仍遵守原退避时间和次数限制，旧版本历史失败继续优先排查。空间不足、worker 恢复工作或运行环境变化时停止。只移除控制器自己加入且非当前播放的条目，释放缓存保护；失败检查点仍参与共享 LRU。`audio_keep_going` 记录此模式，失败与暂缓样本始终留在分母中。

音频通过后，在同一目录取消 `--audio-only` 再运行：仅补同一来源的画面，将已测试的音频流原样封装到独立容器，并检查 PCM 指纹。原音频文件和阶段输入不变，补画面不会使分离和对齐缓存失效；补视频失败也保留原音频和检查点。全部文件及播放验证通过后才计入最终 100 首结果。

逐句音素细化有时会让后一句提前越过前一句。接口会检查全局起点顺序，对冲突行回退到原有粗对齐，并通过 `quality.line_order_fallback_lines` 标记；不会手工平移某个字来凑顺序。粗对齐本身有冲突时不生成伪造的时间轴。

粗对齐修复会同步保存所选窗口的原始词结果，选择记录位于 `alignment/run.json` 的 `boundary_reconciliations`；没有可用预测仍然失败，不通过平移、插值或放宽门槛过关。这项检查保证拼接一致，不代表人工起音准确率。

中文和日文沿用歌声音素与三窗口筛选；英文沿用歌声音素起点和 Whisper 近邻融合。所有语言都使用当前句＋下一句、琥珀色点亮、硬切、片头信息和四秒开唱提示。视频中的旧字幕不参与歌词识别或对齐。

三轨在 float64 中计算，按 `(主唱 + 伴唱) + 背景音乐` 记录未缩放 PCM 的重合误差。普通点歌与 `--playback-audio` 最后将播放器原本接收的共同增益 24 位 PCM 保存为 FLAC，保留原采样率、声道和帧数；完成后临时 WAV 由原有缓存回收流程清除。`audio_storage` 记录格式、原共同增益、原文件哈希及逐轨量化误差，`reconstruction` 仍是压缩前计算的诊断。此时 `shared_preview_gain=1`，防止播放或补视频时重复调低音量。严格 `--audio-only` 验收仍输出未缩放的 float64 WAV。旧 WAV 成品也继续可播。

FLAC 对 24 位 PCM 无损；由 float64 转为 24 位的误差必须不超过一个最低有效位，并与原播放器实际发送的采样值一致。MP3 和 MV 沿用同一个防削波增益。编码试听允许一个 MP3 帧以内的末尾静音填充；缺失音频或新增非静音样本仍失败。重合误差不等于分离纯度，也不证明亮字准确率；结果中这两项没有伪造分数。

MP3 试听使用 LAME 命令行写入完整的尾部填充信息，避免某些末帧长度解码后多出采样。公共增益先应用于临时 24-bit 整数 PCM WAV，避免链接 libsndfile 的 Linux LAME 自动归一化浮点输入；编码完成即删除，原 float64 母版不变。仍按原始采样率、声道、帧数、峰值和尾部静音验证，不通过裁掉验证结果或放宽阈值处理异常。

若有损编码使任一试听轨的解码峰值达到 1，则按实测峰值降低整组公共增益，重新编码所有试听轨；三轨模式也包含 KTV 混音，MV 使用最后验证通过的同一增益。最多编码三轮，仍削波就失败；长度、格式或非静音尾部错误不会触发降增益重试。母版不改动，各轨不单独归一化。

## 配置

### 本机下载、GPU 机器处理

`python -m karaoke.tools.soak audio-fetch --manifest 固定清单 --data-dir 数据目录 --keep-going`
只下载音频并核对来源、哈希和全长解码，沿用普通点歌注册、单实例锁及共享缓存监控。
它将结果写入 `download_attempts`，不会写成 `passed_audio` 或完整 MV 通过；任务记为 `source_ready`，
页面显示尚未准备好，移除控制器自己的点歌项后可正常参与 LRU。再次提交复用来源文件，接着计算。
支持同样的 `--case-url`、`--defer-url`，批量暂停文件为清单旁的 `download.pause`。
登录验证或来源退避必须先解决；遇登录阻塞立即停止后续下载。

迁移时在目标服务正常注册同一来源，再复制该任务的 `source.json`、`download/source.mkv`
和 `download/source.info.json` 到目标任务目录。传输前后核对来源与哈希，保留固定清单和失败历史。
目标服务设置 `KARAOKE_REQUIRE_CACHED_SOURCE=1` 后运行原有 `audio-run`；缓存缺失或损坏立即失败，
不会重新访问媒体下载站点。远程仍需 ASR／文本服务访问和相同模型，音频产物继续逐首完整验证。
离线模式的 LRU 会保留已登记的源音频（包括同时带视频的源容器）、来源信息和轻量诊断，空间不足时先回收计算产物，
任务回到 `source_ready`，后续仍逐阶段核对缓存。源文件也计入同一缓存上限；若仅源文件和
受保护任务就已占满，停止准备，不删除源音频或扩大上限。导入、导出进程须继承相同的离线配置。

`KARAOKE_COMPUTE_CONCURRENCY` 控制每类计算阶段同时运行的数量，默认 1。显存充裕的 GPU 可用 2，让不同歌曲的分离、对齐、封装分别占用最多两个槽位；下载、视频渲染和视频封装仍各用一个槽位。该配置参与流水线版本和阶段检查点，不改变模型精度或窗口 batch；提高前需验证显存及完整产物，歌曲缓存预算仍独立限制入场数量。

`KARAOKE_SEPARATION_BATCH_SIZE` 控制 RoFormer 每次前向计算的音频窗口数，默认 1。
大于 1 时使用批量窗口调用，保持原窗口长度、重叠、尾窗、float32 精度和相加顺序；
没有打开自动混合精度。该设置参与流水线版本及阶段检查点。不同硬件或 batch 的通过数不能合并。
`benchmark_neural.py --inputs` 也支持多条输入共用一次模型加载。ASR 和对齐仍走各自流程，
不能把分离的 batch 设置称为整条流水线批处理；吞吐提升须在目标 GPU 上实测。

### 本地 Whisper 批处理

`KARAOKE_ASR_BACKEND=local` 使用本地 faster-whisper / CTranslate2 的 Whisper large-v3，
模型目录由 `KARAOKE_WHISPER_MODEL` 指定，必须已经下载完整；推理不自动下载模型。
`KARAOKE_WHISPER_BATCH_SIZE` 控制同首歌曲最多并行解码多少个 30 秒窗口（默认 8，范围 1–32）。
包括最后不足 30 秒的片段，覆盖整首音频；不使用可能删掉弱歌声的语音活动过滤。
采用 float32 计算、beam size 5 和固定 temperature 0。自动语言识别从录音中部三个窗口投票。
批次大小、推理库版本和模型文件版本均参与流水线与检查点指纹。

严格 `--audio-only` 的本地模式不请求远程转录、文本整理或音频分类接口，也不在线查找歌词／字幕。普通点歌仍需已有可信歌词或访问已发表的歌词来源。
无声警告的异常检测包含正好挤在片段结束点的零时长词，避免这些词漏过恢复检查；不把下一句的正常词算入前句。
若整句及其前后 250 ms 的有效音频均为数字零，句内完全匹配的词即使挤到文件结束之外，也可随这句一起剔除，并记录其静音父句。没有明确父句、归属冲突、负时间或附近仍有微弱声音时，继续保留异常并走恢复流程，不按音量阈值删词。
保留用户提供的歌词和已下载的同源字幕；否则从本地转录逐字保留文本，仍需通过原有完整性和声学对齐校验。
ASR 固定宽度断行若留下孤立的单字或单词，会在同一短句内平衡末尾两行；不拆开外文单词、不删改文字、不跨原始短句合并，也不调整时间。最终起点仍由声学对齐产生并单独校验。
异常转录可用已有本地 large-v3-turbo 检查同源原音与主唱；恢复失败保留诊断并明确失败。
重复短语即使有正的句时长，若连续重复段落中大多数字词时间已经坍缩，也须恢复或明确失败；正常副歌保留，不能只凭重复次数删词。
没有独立音频分类证据的未覆盖段落仍按原门槛拒绝。ASR 时间用于粗定位，后续由声学模型细化。

在目标硬件上先比较 batch 1 与候选大小的文字和时间，再完成实际歌曲的七项产物验收。
识别 batch 与分离 batch 独立，不能把预下载、识别完成或吞吐对照计为整首音频通过。
局部已知歌词的声学重定位按实际文字选择解码器：中文 SOFA 词表不能表达混合外文时，保留原词和已测量的搜索边界，改用现有多语言 MMS，并记录专用词表拒绝的原因。纯中文继续用 SOFA；资源故障继续上报，两个解码器都无法给出完整有效时间时仍保留失败。
音频控制器保留历史失败；同源预下载在登录失败之后完成，或改用新的本地识别版本解决远程推理阻塞时，
允许新的音频尝试。来源站点的退避仍保留，本地识别不受远程模型配额的退避影响。

单进程、单 GPU 队列运行；不要给同一数据目录启动多个 Uvicorn worker。`none` 模式下所有已点歌曲可进入流水线，同类阶段按 `KARAOKE_COMPUTE_CONCURRENCY` 限制并发，下载和视频编码仍各为一个槽位，不同阶段可以交错；`/health.preparation_concurrency` 返回 `null`，`running_jobs` 和房间快照的 `preparation_jobs` 列出全部在途任务，旧单数属性保留首项。暂停领取任务后，所有已经开始的歌曲仍会自然完成。并发处理各自监控共享缓存，并按运行任务数预留写入余量。独立的分离环境与主环境都需安装对应硬件的 PyTorch。已验证的硬件与依赖组合见 [SETUP](../SETUP.md#2-完整处理环境)，耗时记录见[性能说明](docs/lead-backing-performance.md)。

等待同一工位的步骤按共享待唱列表顺序选择，旧服务端 `current_id` 不再影响准备优先级；已拿到工位的步骤不被打断。每次处理的 `stage-timeline.json` 和成功结果中的 `stage_timeline` 记录相对该 Pipeline 初始化的秒数：`ready`（进入阶段及检查缓存）、`resource_acquired`（取得共享工位）、`started`（开始执行）、`finished`，以及完成／失败／缓存命中状态。缓存命中没有执行时间；工位等待不再混入模型耗时。提交到领取任务的等待另由任务的 `created_at`、`started_at` 计算。部分纯 Python 步骤无工位，只有就绪、开始和结束时间。

新的普通点歌先下载音频；同一次下载写出的元数据立即用于歌词查询。来源信息、同源歌曲名称和已校验的元数据模型结果持久保存，重新准备不会因生成了新任务 ID 而失去名称或重复调用相同模型输入。新鲜的媒体信息可直接用于下载另一条视频流；该路径遇到 429 或登录失败不会静默重新解析网页。媒体下载地址和稳定的歌曲身份分开处理，过期地址不表示元数据丢失。

LINE、网易云和 LRCLIB 的歌词候选不再因歌手名的别名、译名或缺失而被直接排除。歌手名只影响候选排序，LRCLIB 的歌手限定查询没有可用结果时再按歌名查询；正文仍经过既有的来源交叉比较、完整性检查和录音对齐。

维护时可在数据目录创建 `preparation.pause`，暂停领取下一项预处理任务；当前任务正常完成，歌单、排队顺序和缓存保护保持不变。该暂停跨服务重启保留，删除文件后继续，`/health.preparation_paused` 显示状态。批量回归应先暂停控制器，再暂停预处理；定向复现失败样本后才恢复整批。

单首普通点歌取得元数据后即查歌词，音频完成后并行补视频与首轮分离；首轮分离后并行执行主唱分离、对齐用重采样。计算阶段保持原采样率、声道、帧数及 float64 相减，普通播放把背景音乐与伴唱合成底轨，与主唱分别以共同增益保存为 24-bit FLAC。网页 MV 保存字幕画面和微小的静音 AAC 兼容轨，不重复混音或保存音乐。全部必需产物完成后回收分离、解码及封装 WAV；失败时保留有用检查点。`--audio-only` 独立验收仍生成三轨 WAV、三轨 MP3 和字幕。完整流程见 [处理与存储](docs/processing.md)。

服务重启后恢复排队任务；被中断的运行任务标为失败，保留日志和中间文件。失败任务可以重新提交；已完成且文件完整的相同请求直接命中缓存。

播放设备通过现有 `/v1/room/events` 连接的 `playing_entry_id` 报告正在演唱的待唱项；房间快照的 `playing_entry_ids` 仅表示当前连接中的演唱项，不包含播放进度或控制命令。手机置顶和服务端排序都保留这些条目在队首；多个演唱项保持原先相对顺序。停止演唱或关闭连接后释放保护，已移除或与 `job_id` 不符的条目不能获得保护。

## 音乐与视频搜索

`GET /v1/search?q=歌名或歌手&provider=youtube`。只支持 YouTube；不支持的 provider 返回 422。每次返回平台一页的全部可用单视频链接，字段为 `url`、`title`、`uploader`、`thumbnail`、`duration`（秒）、`views`、`provider`、`source_evidence`（来源认证证据，可为空）、`live_status`。后两个字段供离线回归采样筛选；网页搜索不据此过滤。查询限 1–160 字。搜索不创建任务，也不读写歌曲缓存。

前后端保留 YouTube 的结果顺序和数量，没有 3 条截断，不按字面关键词、认证、直播状态额外过滤。仅校验单视频 URL 和封面地址。前端在「YouTube 视频」标签展示，本地曲库在独立标签查看。服务端相同查询和分页游标合并请求，元数据缓存 120 秒、最多 32 项；最多并行 2 个查询、待处理最多 8 个，每次含等待最多 25 秒。超量返回 429，平台错误返回 502，成功无结果返回空数组。复用 yt-dlp 解析一个完整原生搜索页，使用平台 continuation 按需翻页，不重复读取前面的页，无需额外 API key。

`GET /v1/music/search?q=关键词&kind=songs|artists` 用 ytmusicapi 按页读取 YouTube Music 搜索结果，默认参数名保留 songs 以兼容已有客户端，但请求不再添加类型筛选，只向平台传递原始关键词，保留所有类型结果；artists 为用户明确选择的歌手搜索。使用 `zh_CN` 获取平台提供的中文名称。歌曲包含标准 YouTube `url`、`title`、`artists`（名称与可用的频道 ID）、`album`、`version`、`duration`、平台提供的 `views`（可能带万／亿等单位）、`available`、`thumbnail` 和原始 `rank`。歌手返回 `title`、`browse_id`、频道 `url`、`thumbnail`、`rank`；`provider=youtube_music`。不自行翻译名称、自动选择同名歌手或删改版本。

`GET /v1/music/artists/{browse_id}` 只接受 YouTube 频道 ID，读取歌手页及其热门歌单的第一页，返回歌手元数据、`results`、`catalogue_section`、`order`、`complete`。优先歌曲栏目（`songs` / `youtube_music_top_songs`），没有时读取视频栏目（`videos` / `youtube_music_videos`），再没有则保留专辑和单曲发行（`releases` / `youtube_music_releases`），发行仍以专辑类型进入曲目列表。没有歌单链接时保留页面精选并标 `complete=false`。平台未提供播放量时保留空值。前端默认平台顺序并将明确标注的现场版后置；播放量排序仅作用于已加载的、计数可知的结果，未知计数排后。`GET /v1/music/albums/{browse_id}` 接受 MPRE 专辑 ID，返回专辑元数据及完整曲目列表；专辑内默认沿用曲目顺序。以上接口复用视频搜索的限流、超时、缓存与去重，不下载音视频或创建准备任务。

以上三个接口均返回 `results` 和 `next_cursor`（没有下一页为 `null`）；后续请求在相同接口、相同查询参数上附加 `cursor=next_cursor`。歌手元数据仅在第一页返回；`complete` 表示取得热门歌单入口而非只有页面精选，是否加载到底应看 `next_cursor`。每页保留原始顺序，`rank` 连续编号；前端仅跳过与已加载页面重复的同一来源链接，不合并不同版本。游标与查询／类型绑定，只接受服务端签发的随机句柄，有效期 30 分钟，最多保留 256 个；过期、淘汰或不匹配返回 410，重新搜索即可。游标不包含登录凭据，也不接受客户端指定外部地址。前端在列表末尾附近通过 IntersectionObserver 请求下一页，不轮询；同一页只保留一个在途请求。错误不清空已加载结果，不自动循环重试；空页或全重复页但仍有 continuation 时保留手动加载入口。

从结果点歌使用 `POST /v1/room/entries`，例如 `{"url":"视频链接","source_title":"搜索返回的视频标题","source_thumbnail":"https://i.ytimg.com/vi/视频ID/hqdefault.jpg"}`。`source_title` 只给新任务提供临时展示标题（最多 500 字），不参与缓存键，不覆盖后续元数据；用户显式传入的 `title` 仍是优先标题。`source_thumbnail` 只接受来源平台图片域名的 HTTPS 地址，立即保存到 `song_info.thumbnail`；下载元数据也会补充此字段。房间的 `poster` 优先采用可用成品封面，再回退到来源图片，准备状态不阻止显示。处理中的 `song_info` 按字段合并，空对象、空字符串或 `null` 不清除已知信息；下载进度、语言识别等更新不能把已有歌名变回占位文字。已有准备任务优先用 `job_id` 加入。

### 直接对齐的局部恢复

没有 ASR 锚点的直接歌词对齐会单独检查各句。连续坏句使用左右有效句限定的音频上下文重试，最多 45 秒、每块最多 8 次；只替换坏句，原来的有效邻句保持不变。仍有缺句才调用本地 Whisper 定位：一般只识别坏句窗口，大面积错位才识别整块（最多 600 秒），随后最多重对齐 24 个不超过 45 秒的窗口。识别稿不替换歌词；原有效句仅在识别证据指出明显错位时重新对齐。`alignment/raw.json` 的 `line_recoveries` 和 `asr_localizations` 保存窗口、候选、原始结果及接纳／拒绝原因；`quality.recovered_alignment_lines` 记录成功恢复的行。识别结果按来源与模型哈希缓存于 `asr-requests/`。

回退按当前处理已验证的字词结果、原始字词、粗句边界顺序选择。`playback-warning.json` 保存未解决行和 `requires_review`；仍有缺行则返回 `subtitles_failed`，保留音轨和诊断。整份无歌词／纯音乐占位文案不会送入对齐器。

## 两轨播放与存储迁移

普通播放的音频 artifact 为 `accompaniment`（背景音乐＋伴唱）与 `lead_vocals`，音频存储记录 `audio_storage.layout=accompaniment_and_lead`。新 MV 记录 `video_audio=silent_aac`，含静音 AAC 兼容轨；旧的 `video_only=true` 表示历史纯视频容器。`/playback` 返回 `stems`，客户端按列表加载；旧三轨成品仍可播放。所有声部使用同一增益；预览也读取独立音轨。

停止服务后可运行 `python -m karaoke.tools.compact_storage --data 数据目录`，通过同一 `worker.lock` 防止与服务并发迁移。先验证原产物，生成两轨并逐块验证量化误差，核对去音轨前后的全长视频像素哈希，再发布清单与清理中间文件。原处理版本、任务 ID 和歌单不变。相同内容的最终 FLAC/MP4 通过校验后共享硬链接，缓存统计按唯一 inode 计数，单个任务的回收不删除其他引用。

### 歌词可用性预检

`GET /v1/lyrics/availability?ids=视频ID,视频ID` 接受最多 8 个 YouTube 视频 ID，返回 `results` 对象，以 ID 为键。只读取对应录音的 YouTube Music 歌词，不下载媒体、不调用模型、不创建任务，也不返回歌词正文。

每项含 `status=available|unknown`、`checked_at`（真正查询时）、`expires_at`（Unix 秒）和响应时的剩余有效期 `cache_seconds`。浏览器按相对有效期缓存，限制在 30–3600 秒，避免两端时钟不一致或传输期间过期触发循环查询。`available` 带来源、歌词正文哈希；`unknown` 的 `reason` 为 `not_found`、`lookup_failed` 或 `busy`。`not_found` 表示本次在 YouTube Music 未确认到可用歌词；点歌后准备阶段会继续查询其他来源，并执行正文、录音版本与声学检查。

跨用户合并同一 ID 的在途请求，最多 2 个查询同时执行、8 个 ID 在途，每次包含排队最多 25 秒。独立于搜索元数据的并发池，关闭服务会终止查询子进程。缓存最多 512 个 ID：成功 1 小时、未找到 5 分钟、错误 1 分钟；401/403/429 共享来源退避，遵守更晚的 `retry_at`。容量不足直接返回短期 `unknown/busy`，不建立无界等待队列。前端仅批量检查可见歌曲，不轮询刷新状态。
